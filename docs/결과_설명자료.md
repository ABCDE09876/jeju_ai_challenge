# 결과 설명자료: 제주의 두 얼굴

- 대회: 제주 AI·빅데이터 활용 AI Agent 개발 챌린지(제주테크노파크, DAKER)
- 작성 기준: 2026-11-16(마지막 갱신 2026-11-19). 수치는 아래 결과 파일, 로컬 DB, 직접 실행한 테스트에서 확인한 값입니다. 분석 수치는 공식 스키마를 보존한 시드 고정 **합성(시연용) 데이터** 기준입니다(데이터 활용 명세서 8절).

## 심사용 1쪽 요약

**무엇을 하나.** 제주 공공데이터의 단순 평균에 섞인 세 가지 허수(관광객 체류·소비, 낮 평균, 날씨)를 걷어내 도민 실생활 기준의 결론을 내고, 기사·민원 속 통계 주장을 감사하는 에이전트입니다. 질문 한 줄로 로컬 도구 4개(SQLite + pandas)를 실행해 결론과 [원자료로 확인된 수치 사실] / [교란 제거 후 역전 구간] / [원자료 컬럼 부재로 인해 단정할 수 없는 한계 및 현장 확인 질문 1개] 세 구획, 1쪽 증거 카드를 돌려줍니다. 숫자는 로컬 도구만 계산하고, Claude(claude-opus-5-5) 해설 속 숫자는 수치 감사기가 도구 결과와 다시 대조합니다. API Key 가 없거나 장애가 나면 로컬 엔진이 화면 오류 없이 이어받아, 키 없이도 모든 기능이 동작합니다.

**정직하게 밝힌 한계.**

1. 분석 테이블 행의 99.8%는 공식 스키마를 보존한 합성·보정 표본이라, 결과는 실제 제주의 측정값이 아니라 시연값입니다. 센터 원자료를 `data/raw/` 에 넣으면 원자료로 적재되고 출처 표기도 바뀝니다.
2. 벤치마크는 24문항으로 작고 정답 생성기와 도구를 같은 팀이 만들었습니다. 대규모 시험 질문은 문장틀에 값과 입력 변형을 조합한 합성 질문이라 실제 질문 분포와 다를 수 있습니다.
3. 공식 채점 뒤 평가용 오답을 보고 한 수정과 그 점수는 모두 '사후'로 따로 적었고(부록 A), 성적으로 주장하지 않습니다.
4. Claude 경로 답변은 중앙값 36초가 걸립니다(로컬 평균 270.7ms). 수치 감사기는 지어낸 숫자를 모두 잡지는 못합니다(8절 8번).

**실행.** `pip install -r requirements.txt` 후 `streamlit run src/app.py`. GPU·로컬 LLM 없이 CPU 만 쓰고, 로컬 DB 는 첫 실행 때 자동 구축합니다. 모든 시험의 재현 명령은 10절에 있습니다.

**읽는 순서.** 0절(결과 표) -> 1~6절(문제·구조·도구·예시) -> 7절(시험 방법과 공식 결과) -> 8절(한계) -> 9절(센터 활용) -> 10절(재현) -> 부록 A(사후 수정 이력).

## 1. 문제 정의

제주 공공데이터의 단순 평균에는 도민의 실제 생활과 다른 세 가지 허수가 섞입니다: ① 관광객(도외 거주자) 체류·소비가 '활기'를 부풀리고, ② 낮 평균은 밤 9시 이후 생활을 대변하지 못하며, ③ 비 오는 날 퇴근길 혼잡은 연·월 평균에 묻힙니다. 통계 주장·민원에는 집계 방식 변경이 만든 월초 계단식 단절, 측정 컬럼이 없는 원인 단정, 일부 행으로만 계산한 평균(분모 함정)이 더해집니다.

목표는 도민(이사·출퇴근·외출), 시민·기자(주장·민원 검증), 센터 담당자(새 데이터 점검)가 질문 한 줄로 4개 로컬 도구를 실행해 [원자료로 확인된 수치 사실] / [교란 제거 후 역전 구간] / [원자료 컬럼 부재로 인해 단정할 수 없는 한계 및 현장 확인 질문 1개] 세 구획의 답과 1쪽 증거 카드를 받게 하는 것입니다. 필요한 컬럼이나 기간이 없으면 판정을 보류합니다.

## 2. Agent 구조: 하이브리드 자동 폴백

```
[질문 / 원클릭 시나리오 / 후속 질문 버튼 / CSV 업로드]
        |
        v
Streamlit UI (src/app.py): 탭 3개 + 사이드바 브레인 컨트롤러
        |
        v
[Step 0] 로컬 의도·지명 해석 (intent_parser, gazetteer_index)
         자모 퍼지 지명·초성·조사 분리·별칭, 시간·날씨·요일·이용자 슬롯,
         멀티턴 문맥 병합, 판정 보류 사유 탐지
        |
        v
HybridOrchestrator: 모드 판정
   | API Key 있음 + 강제 로컬 아님        | Key 없음 또는 강제 로컬
   v                                     v
[Primary] Claude 경로                   [Local] 로컬 신경-기호 엔진
 claude-opus-5-5, effort xhigh,          plan_tool_calls(의도별 결정론적
 adaptive thinking(summarized)           ReAct 순서) -> run_tool x N
 스트리밍 + Tool Use 수동 루프             -> build_bundle -> 로컬 해설
 -> 같은 4개 도구, 빠진 도구는 로컬이 채움   (외부 호출 0회)
 -> 판정·대시보드는 로컬 규칙                     ^
 -> Claude 해설 + 형식 보완                       |
   |  401·403·404·400·429·5xx/529·네트워크·      |
   |  첫 이벤트 3.5초 초과·거절·출력 한도·빈 응답  |
   +------------------ 자동 폴백 -----------------+
        |
        v
[Core] 4대 로컬 도구 (SQLite + pandas 인메모리 큐브). 모든 수치는 여기서만 계산

        |
        v
number_auditor(해설 숫자 재대조 배지) -> 3구획 해설 + 3단 대시보드
 -> 1쪽 증거 카드(HTML) + 현장 확인 질문 1개 + 후속 질문 버튼 3개
```

주요 파일: `src/config.py`(고정 정책), `src/agent/`(claude_bridge, orchestrator, intent_parser, grounded_synthesizer, number_auditor, response_cache, dialogue_memory, prompts), `src/tools/`(4대 도구, tool_registry, resilient_loader, csv_auditor, db_connector, analysis_cubes, jeju_db_builder, synthetic_seed), `src/ui/`(components, evidence_card, chart_style).

## 7. 검증 방법과 결과

### 7.1 24문항 벤치마크 프로토콜(data/meta/benchmark_items.json, scripts/run_benchmark.py)

- Dev 8문항(D1~D8): 개발 중 규칙·임계값 설계에 실제로 사용(공개). Held-out Test 16문항(T1~T16): Dev 설계 뒤 작성, 결과를 보고 규칙을 고치지 않고 1회 실행 결과를 그대로 보고.
- 정답 근거: 도구 임계값이 아니라 합성 생성기 설계값(심어 둔 은폐 구간 H1~H6, 지역 프로필의 무잡음 기대값 oracle, 배차 설계)과 원자료 보유 기간·컬럼 사전.
- oracle 라벨 사전 검증: 지역 비교 6문항(D1, D7, T1, T2, T3, T15)은 `synthesize_floating(noisy=False)`로 도구 계산과 독립된 기대값을 구해 라벨과 맞는지 미리 확인했고 6/6 일치했습니다.
- 판정 보류 4문항(D8 집값, T5 작년 겨울, T6 월세, T16 2024~2025년 비교)은 보류와 현장 확인 질문 1개를 함께 내야 정답. 오경보 대조군 5문항(D7, T3, T11, T12, T15)은 정상 주장은 confirmed, 설계하지 않은 효과(T11 화요일, T12 첨단단지 장날)는 confirmed가 금지 판정.
- 채점: 금지 판정이면 실패, 허용 판정이어야 하며 추가로 은폐 구간 문항은 심어 둔 정류소·요일군과 시간 겹침, 경계 문항은 경계 20 또는 21시, 단절 문항은 단절 월, 보류 문항은 현장 확인 질문 존재를 확인.
- 엔진: 재현성을 위해 로컬 엔진(결정론, force_offline=True, 캐시 미사용)으로 채점. Claude 경로의 벤치마크 성적은 측정하지 않았습니다(실제 연결 검증은 7.7절).
- 기준선: Baseline 1(단순 평균·엑셀 필터), Baseline 2(단일 표 단순 조회). 주장 속 수치·'때문'을 그대로 받아들이고, 숨은 혼잡엔 평균만 비교하며, 지역 비교는 관광객 포함 평균으로 하고, 판정 보류를 하지 않습니다. 두 기준선은 시간대 필터 여부만 달라 24문항 판정이 모두 같았습니다.
- 지표 묶음: 평균 착시 오판(D1, D2, T1, T2, T4, 실패 건수), 은폐 슬라이스 검출(D3, D4, T7~T10), 함정 차단(D5, D6, T13, T14), 오경보(D7, T3, T11, T12, T15, 실패 건수), 판정 보류(D8, T5, T6, T16).

### 7.4 실패 원인 분석

**T10(은폐 구간 미검출, v1·v2 모두 실패).** 심어 둔 설정은 동문로터리 정류소(9006) 토요일 15~18시 x1.6(H6)입니다. 이 정류소는 업무형으로 생성돼 주말 이용이 평일의 0.6배라, 1.6배를 곱해도 평일 수준의 약 0.96배(0.6 x 1.6)에 그칩니다. 도구 기준선은 '같은 시각 전체 기간 평균'(평일 위주)이라 주말 감소와 토요일 혼잡이 상쇄됩니다. DB 재계산 결과 토요일 15~18시 승하차 평균은 같은 시각 전체 평균의 1.02배(시각별 1.00~1.05배)로 임계값 1.3배에 못 미치고, 같은 시각 일요일보다는 1.61배였습니다(토요일 27일). 은폐 구간이 없으니 판정은 inconclusive가 되어 실패했습니다. v2에서도 고치지 않았고, 같은 요일군(주말) 기준선 대비 배율을 함께 보는 방식이 개선 방향(미구현)입니다.

**T12(정상 대조군 오경보, v1 실패, v2 통과).** 질문의 '오일장'은 날짜 조건(장날)인데 지명 사전의 별칭 '오일장'(도두동)으로 인식돼 비교 지역이 아라동과 오일장 2곳이 됐고, '평소보다'의 '보다'와 '붐'을 두 지역 비교 주장으로 해석해 교란 제거 후 수치 '아라동' 685 vs '오일장' 39를 근거로 "원자료와 일치(정상 주장)"라고 판정했습니다(v1 리포트 결론 문장). 사후 수정으로 질문에 '장날'이 있고 지역이 2곳 이상이면 '오일장' 계열 별칭을 지역에서 빼 날짜 조건으로만 쓰고(`parse_question`, 회귀 테스트 test_market_condition), 조건부 주장은 주어 지역의 은폐 구간만 근거로 씁니다. v2 판정은 inconclusive("주장한 조건에서 '평소보다 붐빈다'는 근거는 원자료에서 확인되지 않습니다")로 통과입니다.

### 7.10 대규모 조합 행동 시험 2,550만 문항(scale_report.json)

**목적.** 7.9절의 5,096문항으로는 지명 166개 표기 x 시간·날씨·요일 표현 x 입력 습관(띄어쓰기 생략, 오타, 초성 등)의 조합을 다 보지 못합니다. 그래서 CheckList(Ribeiro 외, ACL 2020)식 행동 시험으로 정답이 정해진 질문을 대량으로 만들어 해석기를 시험했습니다.

**절차.**

1. 문장틀: 7.9절의 질문 유형 27개를 자리표시자가 든 기본 틀로 만들고(`scripts/scale_suite.py`), 벤치마크·시나리오 문장 30개를 더했습니다. 데스크탑 GPU 의 Ollama 0.34.2 로컬 LLM 이 57개 틀을 7가지 말투로 다시 썼습니다(temperature 0.9, 추론 모드 끔, JSON 스키마, 호출마다 변형 10개, 자리표시자 틀은 (틀, 말투)마다 4번·자리표시자 없는 문장은 2번 호출, 모델마다 1,176회). 자리표시자가 정확히 한 번씩 남았는지, 단위(분·배·년)가 붙었는지, 숫자가 바뀌지 않았는지 검사해 통과한 틀만 썼습니다. gemma4:12b 10,105개(탈락: 중복 1,378, 자리표시자 불일치 214 등)는 개발용, qwen3:14b 7,765개(탈락: 중복 1,811, 자리표시자 불일치 2,065 등)는 평가용입니다.
2. 끼울 값: 지명 166개 표기, 정류소 24곳, 명소·시장 21곳과 시간 41종(시각·시간대), '몇 시 이후' 33종, 날씨 12종, 요일·장날, 이용자 16종, 대기 분, 배수, 연도, 연도+계절 48종, 판정 보류 개념 15종입니다. 값마다 정답 슬롯이 있어 틀에 값을 끼우면 12개 슬롯의 정답이 저절로 정해지고, 조사는 받침에 맞춰 바꿉니다. 기본 틀에 7.9절 기준 질문의 값을 끼우면 기준 질문의 문장과 정답이 그대로 나옵니다(test_scale_suite.py).

**고친 해석기 오류(개발용 오답 기준, 회귀 테스트 test_scale_suite.py).** 띄어쓰기 없이 붙여 쓴 문장의 지명(겹치면 긴 표기 우선, '인구제주시오라동'은 '구제주'가 아니라 '제주시오라동'), 붙여 써도 찾는 띄어 쓴 단서어('몇시에가', '사람많아', '주차공간'), 조사가 붙은 초성 지명('ㄴㅎㄷ이랑'), 전각 영숫자, '비 많이 오는 날', '나이 드신 분', '대기질'의 '대기'를 버스 대기로 읽던 오류, 지명에 붙여 쓴 주제어('건입동카드매출', '노형오거리정류소')까지 지명과 함께 지우던 오류, '동문시장보다'·'주장보다'의 '장보'를 장보기(혼잡)로 읽던 오류, 혼잡 표현('사람 좀 많아', '사람 있어', '사람들로 가득', '여유로워', '덜 복잡', '한가해'), '어느 때·어느 시각에 붐벼'(숨은 혼잡), 방문 시각('몇 시쯤 [장소] 가야 안 붐빌까', '제일 한산해', '붐비지 않는 시각', '사람들이 적은 시간대'), 주장 표현('맞느냐', '진짜 그래?', '~라고 해?'), 생활 탭의 '~하는 거 맞아?'(전해 들은 말이 없으면 주장 검증이 아니라 단순 확인), 후속 시각('7pm 지나면?', '20시 다음은?', 긴 공손한 후속 질문), '밤열한시', 'housing price'. 새 표현이 다른 말에 잘못 걸리지 않게 '한가'는 '한가해·한가한'처럼, '언제 가'는 띄어 쓴 그대로만 찾습니다.

**남은 오답(평가용 공식 채점 뒤 사후 분석, 이것으로 다시 고치지 않음).** 단서어 자체의 자판 오타('저녁 -> 저역·머녁', '퇴근 -> 쾨근·퇴슨', '이후 -> 이허·디후', '사람 -> 사랔'), 평가용에만 넣은 낱말 중 해석기가 모르는 말('연세 드신 분', '애들'은 개발 중 고치지 않아 거의 모두 틀림), 생성 모델이 뜻을 바꾼 틀(어르신을 부르는 '어르신, ~'·'어르신께서는'을 이용자 조건으로 읽음, 주장 표지를 뺀 '<P1> 저녁 도민 수 <P2> 많다?'), 영어로만 쓴 틀, 두 글자 지명의 오타('누형', '애웟')가 대부분입니다. 오타가 다른 단어를 만든 경우도 있습니다('매출은 -> 매출근'에 '출근'이 생겨 버스 주제로 읽음).

**전체 답변 경로 표본과 사후 수정.** 두 세트의 작업 순서 전체에서 고르게 뽑은 299,993문항(중복 제거)을 강제 오프라인·캐시 미사용으로 로컬 엔진 답변 경로 끝까지 실행했습니다(프로세스 15개). 공식 채점 때는 실행 오류 0건, 세 구획 누락 0건, 수치 감사 불일치 1건이었습니다(중앙값 111.0ms, p95 240.8ms, 2,321초). 그 1건은 시민 변호사 탭의 "전기차 충전 내기시간이 평균 40분이라는 보도가 사실인지 친절하게 좀 가르쳐줄 수 있겠나?"였습니다. 원인은 두 가지였습니다.

1. 부탁 말투의 '친절하게'를 '주관적 만족도' 질문으로 읽어 판정을 보류했습니다(개발용 오답에도 있었지만 놓쳤던 원래 오류).
2. 판정 보류 답의 한계 구획에 든 자료 설명 "113행에서만 계산 가능(전체 2,447행의 4.6%)"의 4.6 은 도구 결과에 없는 계산값이라, 수치 감사가 근거 없음으로 표시했습니다(값 자체는 113 / 2,447 = 4.6% 로 맞음).

'친절하게 알려/가르쳐/설명'처럼 부탁하는 말일 때만 판정 보류 단어에서 빼고("버스 기사들 친절해?"는 그대로 판정 보류), 수치 감사가 답의 한계 문구도 근거로 대조하게 고쳤습니다(로컬·Claude 경로 공통). 같은 질문은 이제 thin_denominator(벤치마크 T13 과 같은 판정)로 답하고 수치 감사 14/14 입니다. 이 수정 뒤 같은 25,506,557문항을 다시 채점했습니다(사후, scale_report_posthoc.json). 평가용은 11,019,983 / 12,752,723(86.4%)로 공식과 같고, 개발용은 11,790,479 / 12,753,834(92.4%, 엄격 96.7%)입니다. 전체 답변 경로 표본 299,993문항은 실행 오류·세 구획 누락·수치 감사 불일치가 모두 0건이었습니다(중앙값 110.8ms, p95 241.7ms). 벤치마크 24문항과 퍼징 50문항의 판정·문장·숫자는 이 수정 뒤에도 시간값을 빼면 같습니다. 7.11절 수정까지 넣은 제출 코드로 같은 25,506,557문항을 다시 채점하면(사후 v3, scale_report_posthoc_v3.json, 데스크탑 프로세스 13개 22분 45초) 평가용 11,313,041 / 12,752,723(88.7%, 엄격 91.8%, 부하 81.2%), 개발용 11,869,812 / 12,753,834(93.1%, 엄격 97.2%, 부하 84.3%), 해석기 예외 0건입니다(평가용 오답은 공식 채점 뒤 이미 살펴봤으므로 사후 점수). 7.12절 수정과 그 사후 수정까지 넣은 11-17 제출 코드로 다시 채점하면(사후 v4, scale_report_posthoc_v4.json, 데스크탑과 노트북이 10몫으로 나눔) 평가용 11,313,465 / 12,752,723(88.7%, 엄격 91.8%, 부하 81.2%), 개발용 11,881,818 / 12,753,834(93.2%, 엄격 97.3%, 부하 84.4%), 해석기 예외 0건입니다. 7.13절 수정과 그 사후 수정까지 넣은 최종 제출 코드(해석기 4판)로는(사후 v5, scale_report_posthoc_v5.json, 노트북) 평가용 11,313,656 / 12,752,723(88.7%, 엄격 91.8%, 부하 81.2%), 개발용 11,884,070 / 12,753,834(93.2%, 엄격 97.3%, 부하 84.4%), 해석기 예외 0건입니다.

**속도와 동일성.** 지명 근사 비교에서 자모 분해를 미리 해 두고, 점수 상한(편집 한 번은 자모 2-gram 을 최대 2개 바꾼다는 사실로 구한 편집거리 하한)이 최고점 이하이거나 기준 미만이면 편집거리 계산을 건너뛰고, 2어절 구절 결과를 기억하게 바꿨습니다. 견고성 질문 5,460개를 처음 해석할 때 문항당 7.2ms -> 0.4ms(노트북 단일 프로세스)이고, 데스크탑(16스레드, 프로세스 15개)에서 2,550만 문항 채점이 약 10분(초당 약 4만 문항)입니다(이 절의 공식 채점 때 코드 기준. 7.11절 수정 뒤 제출 코드는 해석 규칙이 늘어 약 20분). 결과가 바뀌지 않는지는 규칙 수정 전 코드에 이 최적화만 넣어 개발용 280,825문항의 해석 결과(QueryPlan 전체)를 원본과 비교해 모두 같음을 확인했습니다. 수정 전 점수는 이 최적화만 넣은 코드로 쟀습니다.

### 7.11 다양성 대규모 시험 7,100만 문항(diverse_report.json)

**목적.** 7.10절의 2,550만 문항은 말투 7종과 입력 습관 11종으로 질문을 넓혔지만, 실제 사용자는 더 다양한 어휘·말투·문장 구조·상황으로 묻습니다. 그래서 "최대한 다양한 어휘, 말투, 문장, 상황"을 기준으로 시험을 새로 설계해 질문 해석기를 71,018,375문항(서로 다른 문장 70,808,539개)으로 시험했습니다(`scripts/diverse_suite.py`, `scripts/run_scale_test.py --suite diverse`).

## 부록 A. 공식 채점 뒤 사후 수정 이력

공식 채점(평가용을 처음 채점한 값) 뒤에 평가용 오답을 보고 한 비교와 수정은 모두 이 부록에 모았습니다. 이 부록의 점수는 평가용 오답을 본 뒤의 사후 점수라 성적으로 주장하지 않으며, 공식 성적은 0절과 7절 본문에 있습니다.

### A.1 1억 시험(7.12절) 뒤: 회귀 4가지 되돌림

**수정이 새로 틀리게 만든 문항(회귀)과 사후 수정.** 공식 채점 뒤 평가용 결정적 등간격 표본 100만 문항을 수정 전 해석기와 공식 채점 해석기로 다시 채점해 문항마다 비교했습니다(16,881문항이 새로 맞고 103문항이 새로 틀림). 이어 데스크탑과 노트북이 평가용 50,012,374문항 전부를 수정 전 해석기와 사후 수정 해석기로 나눠 채점해 같은 비교를 했습니다. 수정 전 해석기의 전수 오답은 4,682,551개로, 동결해 둔 수정 전 점수(45,329,823 / 50,012,374)와 문항 수까지 같습니다. 새로 틀린 문항은 다음과 같습니다.

1. 정한 시기가 붐볐는지 묻는 평가용 문장틀 하나('2018년 가을 추자 쪽 버스가 특히 붐비는 시기였던 것으로 알고 있나요?'와 그 변형, 표본 96문항, 이 유형 576,300문항 전수로는 5,054문항): 개발용 '평소엔 괜찮은데 주말에 좀 심하게 붐비는 시기 있나요?'를 고치려고 숨은 혼잡 표현에 '시기'를 더한 것이, 정한 시기가 그랬는지 묻는 말까지 숨은 혼잡 질문으로 읽게 했습니다. '기간 판정 보류' 유형이 내려간 원인입니다.
2. 지명 오타 '한결에서'(한경, 표본 1문항): '환경에서'가 한경으로 읽히지 않게 불용어를 조사를 뗀 꼴로도 보게 했더니, 불용어인 부사 '한결'에 조사가 붙은 지명 오타까지 지명에서 빠졌습니다.
3. '충격적'의 오타 '충경적'(전수 비교에서 드러남): '클랙슨 소리'를 고치면서 같은 뜻의 '경적'을 소음 개념에 더했는데, '충경적이야' 속 '경적'까지 걸려 판정 보류가 됐습니다.
4. '진짜'의 된소리 오타 '찐짜'(전수 12문항): 주장 확인 단서 '~다는 거 찐(임)?'이 '편하다는 거 찐짜?'에도 걸려 주장 확인으로 읽었습니다(오타 없는 '편하다는 거 진짜?'는 일반 질문).
5. 라벨 잡음(전수 458문항): 문장틀 자체가 자료 목록이나 원인·숨은 혼잡을 묻는데 라벨이 다른 틀입니다('할머니 기준으로는 어떤 대이터가 있나요?'·'급증했다는 주장, 어떤 대이터로?'·'뭐 떼문이야?'·'도민들 떼문인가요?'·'언재 방문하면 혼잡하지 않을까?'). 모음 혼동 오타를 바로잡자 오타 없는 같은 문장과 같게 읽혔고, 수정 전 해석기도 오타 없는 문장은 이렇게 읽습니다. 그대로 뒀습니다.
6. 오타가 다른 단서어를 만든 문장(전수 4문항): '제출'의 오타 '메출'이 '매출'의 모음 오타 꼴이 되거나, '이호동을'의 오타 '이호동틀'에 '동틀'(새벽)이 생기거나, '어제'의 받침 오타 '언제'로 숨은 혼잡 질문이 된 경우입니다. 막으려면 정상 문장을 깨뜨릴 위험이 커서 그대로 뒀습니다.

1~4는 이번 수정이 만든 회귀라 공식 채점 뒤 되돌렸습니다(사후 수정. 평가용 오답을 본 뒤의 수정이므로 이후 점수는 사후 점수입니다). '붐비는 시기'는 뒤에 '있·잇·가·는·언제·알려' 같은 말이 와서 그런 시기가 있는지나 언제인지 물을 때만 숨은 혼잡으로 읽습니다. 불용어를 조사를 뗀 꼴로 볼 때 부사 '한결'은 빼고, '경적'은 낱말 첫머리나 '차·차량·버스·택시' 바로 뒤에서만 소음 개념으로 보며, 주장 단서를 볼 때만 '찐짜'를 '진짜'로 읽습니다. 처음에는 '시기' 뒤에 서술격 조사('였·인가·이야')가 오면 빼도록 고쳤지만, 같은 유형 전수에서 서술격 조사에 오타가 난 132문항('시기여던'·'시기얐던')을 놓쳐 허용 목록 방식으로 바꿨습니다. 사후 수정 확인:

- 평가용 50,012,374문항 전수(최종 코드, 데스크탑과 노트북이 나눠 채점): 수정 전 해석기와 문항마다 비교해 새로 맞은 문항 838,955개, 새로 틀린 문항 462개(위 5번 라벨 잡음 458개와 6번 오타가 만든 단서어 4개). 최종 오답은 3,844,058개(정답 46,168,316 / 50,012,374, 92.3%)입니다.

- 개발용 30만 표본과 7.11절·7.10절 개발용 20만 표본: 공식 채점 해석기와 문항 하나까지 같습니다.
- 1억 문항 전체에서 공식 채점 해석기와 비교: 두 해석기는 위 네 규칙만 다르고, 해석기 정규화(이모지 제거, 단서어 17개의 모음 혼동 교정)는 '시기'·'한결'·'경적'·'찐짜'를 새로 만들지 못합니다. 그래서 1억 문항을 모두 만들어 질문과 앞 질문의 한글에 네 낱말 중 하나가 든 문항(개발용 338,460개, 평가용 108,171개)만 두 해석기로 채점했습니다. 평가용은 5,171문항이 새로 맞고('시기' 5,055·'한결' 97·'찐짜' 15·'경적' 4) 2문항이 새로 틀렸고, 개발용은 새로 맞은 문항 없이 3문항이 새로 틀렸습니다. 새로 틀린 5문항은 모두 '붐비는 시기' 뒤 말의 오타가 허용 목록에 없는 경우입니다('시기는'의 오타 '붐비는 시기느/시기눈 언제인가요?', '시기 있나요'의 오타 '붐비는 시기앗나여/시기깃나여/시기일나여??'). 오타 꼴을 하나하나 허용 목록에 더하는 것은 이 시험 문장에 맞춘 수정이라 더 고치지 않았습니다. 작업별 오답 수 차이는 아래에서 다시 채점한 몫 파일과 작업 하나까지 같습니다.
- 확인 문장과 대조 문장 10개를 회귀 시험 표(`tests/test_mega_regressions.py`)에 더했습니다.

### A.2 6천만 시험(7.13절) 뒤: 2판·3판·4판

**수정이 새로 틀리게 만든 문항(회귀)과 사후 수정.** 공식 채점 뒤 데스크탑과 노트북이 평가용 30,005,386문항 전부를 수정 전 해석기와 공식 채점 해석기로 다시 채점해 문항마다 비교했습니다. 두 해석기의 전수 오답(3,035,595개와 2,193,483개)은 동결해 둔 수정 전 점수와 공식 점수에 문항 수까지 같습니다. 새로 맞은 문항은 844,842개, 새로 틀린 문항은 2,730개(문장틀 64개)입니다. 새로 틀린 문항은 기계적으로 두 갈래로 나눴습니다. 최종 해석기의 새 정규화(겹친 띄어쓰기·한영 복원·말버릇·연음·띄어쓰기 잇기·한자어 수사)를 거친 문장을 수정 전 해석기에 넣어도 최종 해석기와 같은 답이 나오면 '정규화' 갈래이고, 아니면 이번에 바꾼 해석 규칙이 답을 바꾼 '규칙' 갈래입니다.

1. 규칙 갈래 2,280문항(문장틀 4개): 숨은 혼잡 새 표현 '사람이 많은 시간대'가 정한 기간에 그랬는지 묻는 '선생님, 2021년 겨울 삼화지구 버스가 사람이 많은 시간대가 있었던 것 같나요?'(1,609문항)와, 덜 붐비는 때를 묻는 '…장을 방문할 때 덜 사람이 많은 시간대를 알려주세요.'(669문항)에도 걸렸습니다. 지명 잡음 '연도' 규칙은 '제주시 연도 가까운 데'(띄어 쓴 다음 낱말 '가까운'의 '가')와 '제주 연도의 아파트'(연동의 오타)에도 걸렸습니다(2문항).
2. 정규화 갈래 450문항(문장틀 60개): 대부분은 되살린 문장이 문장틀 원문과 같고, 수정 전 해석기도 그 원문을 같은 답으로 읽는 경우입니다. 예를 들면 한영 복원으로 되살린 '그건 정말입니까?'·'~것이 사실입니까?'를 주장 확인으로 읽었는데 라벨은 일반 질문인 틀, '그 날이 조을 것 같아'를 '좋을'로 되살려 날씨 좋은 날로 읽은 틀, 사극 말투 '붐비오리까' 속 '비오'를 비 오는 날로 읽은 틀, 문장틀이 쓴 지명 '제주 이도동'이 라벨에 없는 틀입니다. 다만 10문항은 정규화가 원문과 다르게 바꿨습니다. '오후 다섯 시 사십오 분쯤'의 분만 '45분'으로 바꿔 대기 시간으로 읽은 6문항, 띄어쓰기 없이 한글에 붙은 영어 낱말('workfor아동', 'toWifi사용자')을 한글로 바꾼 2문항, 오타가 다른 단서어를 만든 2문항('좀'의 오타 '점'과 '심심'이 이어져 '점심', '바는'의 오타 '바믄'을 '밤은'으로 읽음)입니다.

규칙 갈래와 분 6문항은 이번 수정이 만든 회귀라 공식 채점 뒤 고쳤습니다(사후 수정. 평가용 오답을 본 뒤의 수정이므로 이후 점수는 사후 점수입니다). 처음 만든 사후 수정은 숨은 혼잡 표현 뒤에 올 말을 좁게 나열하는 방식이었는데, 문항마다 비교하니 공식 채점 해석기가 맞히던 '평소엔 괜찮은데 장날엔 특히 사람이 많은 시간이 있지?·있는가?' 같은 7,692문항을 새로 틀리게 해 버렸습니다. 그래서 공식 채점 해석기의 규칙은 그대로 두고 회귀 원인만 막도록 다시 고쳤습니다.

- '사람이 많은 시간대' 표현은 질문에 낱말 머리의 '덜'(또는 붐빔 낱말 바로 앞에 붙은 '덜')이 있거나 연도('2021년'·'작년'·'재작년'·'지난해'·'올해'·'금년')를 짚으면 숨은 혼잡으로 보지 않습니다. 오타 지명 '국제여객선터미덜' 속 '덜'은 보지 않습니다.
- 지명 잡음 '연도'는 조사(는·가·를·와·로·도)가 낱말 끝일 때만 보고, '의'는 뺐습니다('연도 별'은 그대로 봅니다).
- 숫자가 아닌 시각('다섯 시 ') 바로 뒤의 분은 숫자로 바꾸지 않습니다. '십팔 시 영 분'처럼 시각이 먼저 '18시'로 바뀌면 분도 바꿉니다.
- 한글에 붙은 영어 낱말 2문항은 고치지 않았습니다. 처음 사후 수정에 넣었던 규칙(한글에 붙은 영문은 지명이나 단서어로 풀릴 때만 되돌림)이 평가용 전용 변형 '지명 한영 전환'('rnehtla이랑' = '구도심이랑' 같은 지명 일부)을 수백 문항 새로 틀리게 했기 때문입니다. 오타가 만든 단서어 2문항과 '덜'의 오타('더'·'떨'·'둘') 5문항도 오타 꼴을 막는 것이 이 시험 문장에 맞춘 수정이라 그대로 뒀습니다.

사후 수정 확인(2판):

- 평가용 30,005,386문항 전수(노트북): 공식 채점 해석기와 비교해 새로 맞은 문항 2,389개(위 회귀 2,281개와, 회귀에 가려 있던 같은 두 문장틀의 108개), 새로 틀린 문항 0개입니다. 수정 전 해석기와 비교하면 새로 맞은 문항 844,950개, 새로 틀린 문항 449개(정규화 갈래 444개와 '덜'의 오타 5개)입니다. 오답은 2,191,094개(정답 27,814,292 / 30,005,386, 92.7%)입니다.
- 개발용 200만 표본(결정적 등간격): 공식 채점 해석기와 문항 하나까지 같습니다. 수정 전 해석기와 비교하면 새로 맞은 문항 32,341개, 새로 틀린 문항 34개이고, 34개는 모두 정규화 갈래의 라벨 잡음입니다.
